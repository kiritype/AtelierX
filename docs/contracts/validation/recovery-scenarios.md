# 접수·저장·복구 검증 조건

상태: 구현 전 검증 명세. 상태 전이 trace만 실행했고 아래 파일/프로세스/네트워크 장애는 **아직 실제 시험하지 않았다**.

## 영속 기록 초안 보완

ADR-0019의 작업 파일·접수 키·Queue가 각기 별도 파일이면 단순 원자적 rename 하나로 전부 일관되게 갱신되지 않는다. 따라서 단일 프로세스의 단일 기록 주체가 **한 Job의 원본 기록에 접수 주체·키·요청 fingerprint·고정 입력·상태·revision·실행 식별을 함께 저장**하고, Queue와 키 조회 인덱스는 원본 기록에서 복원하는 안으로 구체화한다.

접수 응답은 원본 기록의 내구성 있는 반영 이후에만 반환한다. 결과 파일을 먼저 완성하고 그 참조를 원본 기록에 반영한 뒤 terminal 상태를 공개한다. 파일 flush·원자적 교체·디렉터리 내구성은 OS별 시험이 필요하며 Windows rename만으로 전원 차단 내구성을 보장하지 않는다. 여러 Validation 프로세스가 같은 작업 디렉터리를 쓰는 방식은 초기안에서 지원하지 않는다.

## 구현 후 통과해야 할 시나리오

| 장애/경쟁 | 기대 결과 |
| --- | --- |
| 원본 기록 전 종료 | 접수 완료를 응답하지 않음. 실행 없음 |
| 기록 후 응답 유실 | 키 조회로 기존 Job 발견, 중복 실행 없음 |
| 같은 주체·키·본문 동시 접수 | 원본 Job 하나와 동일 Job ID |
| 같은 키·다른 의미 본문 | 409, 기존 요청 변경 없음 |
| 다른 주체의 같은 키 | 서로의 Job 노출 없이 독립 접수 |
| Queue 인덱스 쓰기 전 종료 | 원본 queued 기록에서 복원 |
| Provider 제출 직후 종료 | 제출/실행 식별로 확인. 불명확하면 failed, 자동 재제출 없음 |
| 결과 저장 후 terminal 반영 전 종료 | 무결한 결과와 실행 기록 확인 후 복원, AI 재호출 없음 |
| 취소와 결과 도착 경쟁 | 원본 revision으로 순서 결정. 먼저 취소가 반영됐으면 늦은 결과 자동 적용 없음 |
| 기준 변경과 결과 등록 경쟁 | 이전 기준 결과는 이력, 현재 유효 결과로 덮어쓰기 없음 |
| Core 결과 수신 후 확인 유실 | job_id 기반 중복 등록 방지, 결과 재조회 가능 |
| 업로드 정리와 새 참조 접수 경쟁 | 원자적으로 참조 보호 또는 만료 거부. 실행 중 파일 삭제 없음 |
| 접수 키 정리 시 활성 Job 존재 | 정리하지 않음 |
| 디스크 부족/삭제 실패 | 원본·활성 입력 보존, 명시 오류·관리 진단. 기록 유실을 정상 완료로 응답하지 않음 |

권한 실패·revision 충돌·접수 응답 유실을 Provider 오류로 꾸미지 않는다. 자동 네트워크 재전송과 사용자 명시 재검증을 구분한다. 서버에 없거나 만료된 키로 같은 실행을 재접수할 위험은 키 보관 계약과 클라이언트 재조회 절차에서 다룬다.
