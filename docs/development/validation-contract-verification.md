# Validation 계약 검증 — 2026-09-13

사용자 지시로 ADR-0019의 입력·응답 Schema와 상태 전이·복구 검증 자료를 구체화했다. [계약 진입점](../contracts/validation/README.md)을 따른다. Backend API·DB·Provider·GPU 실행 구현은 추가하지 않았다.

## 현재 범위 정정

사용자는 이후 현재는 ADR 검토 단계임을 명확히 했다. 아래 실행 이력은 사실대로 보존하되 구현 착수/계약 확정으로 취급하지 않는다. Validation 후속 작업은 문서 검토에 한정하며 검사 코드를 더 작성하거나 실행하지 않는다.

## 결과

- JSON Schema 2020-12 5종 생성: 단일/묶음 요청, 단일/묶음 결과, Job.
- 정상 예제 10개: 단일 합격·불합격·변경 제안 없음·오류, 묶음 부분 실패·부분 재검증, 요청·Job 상태.
- 기존 ComfyUI venv의 Pydantic v2를 사용한 18개 계약 검사 통과. 새 의존성 설치 없음.
- 필수/추가 필드, 잘못된 참조·중복 참조, 요청/결과/Job 연결, 기준 revision·설정 변조, 잘못된 변경값, 오류와 재생성 혼합, 집계 모순·비교 불충분 은폐를 검사했다.
- 상태 전이 trace에서 대기 복원·실행 재연결·추적 불가 실패·취소 후 늦은 응답·Timeout 뒤 재실행 금지를 확인했다.

## 발견·정리한 사항

1. Job 처리 상태와 이미지 판정을 분리했다. 묶음 이미지별 오류가 다른 정상 결과를 삭제하지 않게 했다.
2. 부분 재검증의 전체 일치는 해당 요청 범위만 의미한다. 현재 그룹 전체 집계는 Core가 현재 기준과 대상에 맞춰 수행한다.
3. 요청과 결과가 각각 유효하더라도 다른 Job·이미지·기준·Provider 설정에 연결되면 거부하도록 교차 검사를 추가했다.
4. ADR-0019의 여러 상태 파일을 단순 rename으로 동시에 갱신할 수 없으므로 Job 원본 기록을 단일 권위 기록으로 두고 인덱스를 복원하는 상세 초안을 작성했다.

## 검증 한계·다음 단계

JSON Schema에 표현되지 않은 집계·연결 규칙은 실행 모델의 추가 검사로 확인했다. 생성 환경의 capability·실제 파일 digest·권한·시각 판정 품질은 아직 시험하지 않았다.

실제 프로세스 중단·디스크 오류·중복 접수 경쟁·Core 결과 등록·GPU 공유 복구는 [복구 검증 명세](../contracts/validation/recovery-scenarios.md)에 기대 결과만 정리했다. 테스트 통과는 실제 영속 복구 성공을 뜻하지 않는다. 전체 OpenAPI, 체크별 실행/생략 보고, 운영 서비스의 접수 응답·SSE·권한 계약은 후속 보완한다.

다음은 이 초안을 기반으로 API 전체 계약을 보완하고, Backend 구현이 지시되면 접수·저장 프로토타입에서 복구 시나리오를 실행하는 것이다. ADR-0005·0019는 Proposed를 유지한다.
