# 제작 화면 상세와 수용 기준

기록일: 2026-09-13. [전체 구성](frontend-structure.md)은 사용자 합의 사항이다. 아래 편집 상태·입력 순서·오류 동작은 기존 요구와 API에 맞춘 **상세 구현 초안**이며 화면 구현 완료를 뜻하지 않는다. 픽셀 단위 디자인·Framework·새 저장 API는 정하지 않는다.

## 화면에서 구분할 세 가지 데이터

| 구분 | 예시 | 저장·적용 범위 |
| --- | --- | --- |
| 원본 편집 | 작품/캐릭터 이름, 캐릭터 Negative, 의상 외형·상의·하의 | Core에 명시적으로 저장하고 revision 갱신 |
| 이번 생성 입력 | 표정·자세·구도·상황·포함 항목, 모델·LoRA·후처리·검증 선택 | 접수 전 화면 초안, 접수 후 Task/Batch snapshot |
| 실행 결과 | 최종 Prompt·설정, 이미지, 검증·시도 이력 | 읽기 전용 이력; 현재 설정으로 소급 표시하지 않음 |

원본 의상을 저장해도 이전 그룹은 바뀌지 않는다. 선택한 그룹의 고정 구성과 현재 의상 원본이 다르면 이를 표시하고, 현재 원본으로 생성할 새 그룹과 과거 그룹 사용을 구분한다. 분류 선택만으로 그룹을 자동 생성하지 않는다. 이전 그룹 선택은 구현된 `GET /v1/groups?outfit_id=...`를 사용한다. [조회 API 검증](core-browse-api.md)을 참조한다.

## 왼쪽 — 분류 탐색·관리

작품 > 캐릭터 > 의상을 펼쳐 선택한다. 항목별 이름·추가·편집·보관을 제공한다. 영구 삭제와 보관은 다른 기능이며 현재 화면 기본 동작은 기존 보관 API를 사용한다. 미저장 원본 편집 상태에서 항목을 바꾸려면 저장 후 이동/편집 유지/변경 버리기를 선택할 수 있게 한다. 저장 실패 시 선택을 이동하지 않고 입력을 유지한다.

작품만 선택하면 분류 정보, 캐릭터를 선택하면 캐릭터 정보와 Negative, 의상을 선택하면 3개 Prompt 편집과 생성 작업 영역을 연다. 의상이 없으면 생성 버튼 대신 의상 준비 안내를 표시한다. 트리 조회 실패와 실제 빈 목록은 구분한다.

## 가운데 위 — 저장할 Prompt

| 선택 항목 | 편집 영역 | 주의할 의미 |
| --- | --- | --- |
| 작품 | 이름 등 분류 정보 | 생성 Prompt가 아님 |
| 캐릭터 | 이름 등 분류 정보, 캐릭터 Negative | 이미지에 있으면 불합격시키는 금지 요소 |
| 의상 | 외형 / 상의 / 하의 | 하의에 풋웨어 포함; 액세서리 별도 입력 없음 |
| 전역 적용값 | Positive·Negative 읽기 전용 요약, 설정 이동 | Negative는 품질용 생성 조건이며 검증 불합격 기준으로 사용하지 않음 |

의상 `components`는 서버 계약에 따라 3개 필드를 함께 저장한다. 한 필드 편집 시 다른 필드 내용을 잃지 않으며 revision 충돌은 최신 서버 원문과 사용자 초안을 나란히 확인할 수 있게 한다. 충돌 응답 뒤 자동 덮어쓰기는 하지 않는다.

## 가운데 아래 — 이번 생성

단일/일괄 입력을 전환한다. 단일 입력에는 구도, 표정, 자세·동작, 상황, 의상 구성 포함 여부를 둔다. 현재 지원 구도는 upper_body와 full_body다. 자유 문자열은 Core에 전달하고 브라우저에서 번역·태그 조합·Prompt 재작성을 하지 않는다.

upper_body에서는 하의 제외를 표시하고, 숨겨진 상태로 lower=true를 전송하지 않는다. 포함/제외의 최종 사유는 Core preview 결과를 따른다. full_body로 돌아왔을 때 적용할 선택값은 화면 초안으로 보존하고 다시 preview한다.

일괄 입력은 행 추가·복제·제거로 구성한다. 각 행은 구도·표정·자세·상황과 선택 여부를 가지며 공통 생성·후처리 설정은 선택한 행들에 적용한다. 이는 입력 양식의 복사이며 브라우저가 생성 순서나 검증·재생성을 조정하는 것이 아니다. 접수 직전 모든 행의 실제 요청과 Core preview를 확인하고 한 Batch API로 제출한다.

현재 Batch API는 한 그룹의 1..32개 항목과 단일/묶음 검사 선택을 요구한다. 생성 전용 일괄 실행이나 여러 그룹을 한 Batch에 넣는 UX를 구현된 기능처럼 표시하지 않는다. 이 요구를 확장하려면 Backend 계약 공백으로 기록한다. 표정 등의 영구 카탈로그 저장도 현 API에 없으므로 자유 입력과 행 복사를 제공하는 범위로 시작한다.

최종 프롬프트 미리보기는 Core가 반환한 Positive/Negative, 실제 포함 요소와 제외 사유를 표시한다. 편집한 입력에 해당하는 최신 응답만 반영하고 이전 요청의 늦은 응답으로 덮어쓰지 않는다. 미리보기는 확인 가능한 펼침 영역으로 두며, 매번 별도의 승인 팝업을 추가하지 않는다.

## 오른쪽 — 실행 설정

1. 생성 설정: Preset 또는 직접 입력을 선택한다. Anima 모델·encoder·VAE·sampler·scheduler의 실제 등록 선택지를 사용한다. 준비되지 않은 모델 계열은 사용 가능으로 표시하지 않는다.
2. LoRA: `+`로 행 추가, `-`로 제거하며 각 행의 이름과 가중치를 편집한다. 배열 순서를 보존한다. 기존 등록 목록에 없는 항목은 오류 상태로 보여 주고 다른 모델로 바꾸지 않는다.
3. 해상도·숫자 설정: 기본 1024×1024, Seed·Steps·CFG. Core 범위와 검증 오류를 표시하고 부정확한 임의 보정을 하지 않는다.
4. 후처리: 기본 설정 사용 / 직접 설정 / Preset을 구분한다. 기본은 4x UltraSharp 모델을 사용한 최종 1.5배 Upscale 및 WebP 출력이다. 1024×1024일 때 최종 1536×1536을 구분해 표시한다. 후처리 없음은 명시적 빈 객체이며 설정 생략과 다르다.
5. 직접 후처리: Upscale, Detailer, Censor, Alpha, Encode 옵션을 기존 API 범위로 편집한다. PNG는 기본 출력, WebP는 On/Off·품질 선택이다. stage 순서는 Backend 고정이며 임의로 재배치하는 UI는 제공하지 않는다.
6. 검사 선택: 단일 Task의 생성만 / 생성 후 검사, Profile·Provider와 적용 revision을 표시한다. 묶음 검사는 Batch 계약과 연결한다. 자동 재생성 on/off·상한은 적용 전역 값과 설정 이동을 제공하며 새로운 Task별 override를 만들지 않는다.

선택한 Preset과 같은 종류의 직접 설정은 동시에 제출하지 않는다. Preset 수정은 원본 저장이고 이번 실행에서 값을 바꾸는 동작과 구별한다. Preset에서 직접 입력으로 전환하는 초안 동작은 선택된 revision 값을 복사하되 Preset을 자동 저장하지 않는다.

## 저장·미리보기·실행과 상태

| 상태 | 화면 동작 | 수용 기준 |
| --- | --- | --- |
| 분류/연결 미준비 | 필요한 항목 안내, 실행 비활성 | 실패한 목록을 빈 데이터로 바꾸지 않음 |
| 원본 미저장 | 저장/버리기와 적용 그룹 차이 안내 | 저장 안 된 의상을 저장된 것처럼 생성하지 않음 |
| 생성 입력 변경 | 미리보기 갱신 필요 표시 | 변경 전 preview hash를 실행에 재사용하지 않음 |
| 미리보기 오류 | 해당 필드 및 오류 이유 표시 | 초안을 유지하고 실행하지 않음 |
| 실행 접수 중 | 동일 제출 버튼 중복 실행 방지 | 같은 요청의 키를 유지; 입력을 바꾼 새 요청과 구분 |
| 접수 응답 유실 | 기존 요청 확인 중 표시 | 지원되는 key 조회로 확인; 새 키의 중복 작업을 만들지 않음 |
| revision/preview 충돌 | 최신 상태 재조회, 차이와 재확인 안내 | 자동으로 새 기준을 승인하거나 덮어쓰지 않음 |
| 접수 완료 | 화면 유지, Task/Batch 링크 제공 | 작업 완료 대기와 다음 입력 편집을 분리 |
| 생성/검증 완료 | 최종 결과 요약과 상세 이동 | 상태·오류·현재/과거 기준을 구분 |

첫 제출 전에 Shared Client가 최신 Core preview를 받아 해당 hash로 접수할 수 있다. 사용자가 확인하지 않은 stale 변경이 발견되면 변경 내용을 표시하고 재확인한다. Task 조회와 Batch 접수 복구는 각 API의 실제 지원 경로를 따른다. 모든 mutation에 동일한 key 조회 endpoint가 있다고 가정하지 않는다.

## 후속 구현 검증 시나리오

- 작품 이름을 바꿔도 작품명이 생성 Prompt에 삽입되지 않는다.
- 의상의 상의만 편집해 저장해도 외형·하의 원문이 유지된다.
- 기존 그룹과 다른 의상 revision을 저장해도 과거 이미지·Task는 바뀌지 않는다.
- upper_body 미리보기에 하의가 제외되고 full_body 변경 뒤 새 preview 결과로 접수된다.
- LoRA 여러 행을 추가/제거해도 남은 이름·가중치·순서가 유지된다.
- 기본 후처리, 없음, 명시적 설정, Preset을 각각 다른 의도대로 전송한다.
- 일괄 요청은 모든 행을 검토한 뒤 한 번 접수되고 UI가 검증/재생성을 중복 호출하지 않는다.
- 접수 버튼 연속 클릭·응답 유실·설정 revision 변경에도 초안과 작업 이력이 보존된다.
- 다른 메뉴로 이동했다 돌아오면 선택·필터·편집 문맥을 유지한다. 페이지 새로고침/브라우저 종료 후의 초안 보존 범위는 별도 저장 설계이며 이번 합의에 포함하지 않는다.

기존 REST 지원 및 조회 API 보완 이력은 [메뉴별 API 대조표](frontend-menu-api-map.md)를 따른다. 이 시나리오는 앞으로의 화면/API 수용 기준이며 실제 UI 테스트를 실행했다는 기록이 아니다.
