# 0022. 1.0 전에는 새 기능에 MINOR, 개선·수정에 PATCH를 올리고, 다음 버전만 마일스톤으로 묶는다

- 날짜: 2026-10-06
- 상태: 채택

## 결정

버전은 `MAJOR.MINOR.PATCH`(시험판은 `-rc.N`, [0020](0020-branch-flow.md))이다. 1.0 전에는 다음 기준으로 올린다.

| 올리는 자리 | 언제 | 예 |
|---|---|---|
| `0.MINOR.0` | 새 기능, 데이터 형식(`layout_version`·`schema_version`) 변경, 결정 기록이 새로 생기거나 바뀌는 변경 | 파일 단위 가져오기, 배포 업로드 |
| `0.x.PATCH` | 기존 기능의 개선·UX, 버그 수정, 문서, 리팩터링 | 버튼 모양, 안내 문구, 설명서 페이지 |

- 한 릴리스에 MINOR 감인 변경이 하나라도 있으면 MINOR를 올린다.
- 데이터 형식이 바뀌는 릴리스는 변환 도구를 함께 낸다([data-model 버전](../data-model.md#버전)).
- **마일스톤**: 다음에 낼 버전만 만들고, 그 버전에 넣기로 한 이슈만 단다. 일정이 없는 이슈는 마일스톤 없이 둔다.
- **릴리스 조건**: 마일스톤의 이슈가 모두 닫히고 시험판(rc) 확인이 끝나면 정식으로 낸다. 확인 중 빠진 이슈는 다음 마일스톤으로 옮긴다.
- **1.0 조건**: 데이터 형식을 이후 버전에서 읽을 수 있게 유지한다고 약속할 수 있을 때. 그 전에 다른 PC에서 실행 검증과 주요
  외부 서비스(LLM 제공자, 인터넷 이미지 서비스) 실제 확인을 마친다.
- 1.0 이후에는 일반적인 유의적 버전을 따른다(호환이 깨지면 MAJOR).

## 이유

- 지금까지는 기준 없이 올려서, 0.1.0처럼 기능이 크게 들어간 릴리스와 0.0.x의 수정 릴리스가 번호로 구분되지 않았다.
- 사용자는 앱 안 업데이트로 버전을 받는다. MINOR가 바뀌면 새 기능이나 데이터 변환이 있다는 것을 번호만 보고 알 수 있어야 한다.
- 모든 이슈에 버전을 미리 매기면 계획이 바뀔 때마다 고쳐야 한다. 다음 버전만 묶으면 릴리스 범위가 이슈 목록에서 바로 보인다.

## 결과

- 기여 안내([CONTRIBUTING](../../CONTRIBUTING.md))에 이 기준과 마일스톤 쓰는 법을 적는다.
- 릴리스 노트는 마일스톤의 이슈를 바탕으로 쓴다.
