# 0020. 작업 브랜치 → dev → staging → main으로 올리고, 검증한 파일을 그대로 릴리스한다

- 날짜: 2026-10-05
- 상태: 채택

## 결정

- 작업은 `feat/*`·`fix/*`·`docs/*`·`ci/*` 브랜치에서 한다. 작업 하나에 브랜치 하나, **작업 폴더(git worktree) 하나**를 쓴다.
  여러 사람·도구가 같은 작업 폴더를 같이 쓰지 않는다.
- `dev`: 작업 브랜치는 PR로만 합친다. 승인은 필수가 아니고 CI `test` 통과는 필수다. 합치는 방식은 squash 또는 rebase
  (기록을 한 줄로 유지).
- `staging`: 검증할 `dev` 커밋 하나로 **fast-forward**해서 후보로 고정한다. push되면 CI가 패키지를 만들어 시험판
  `vX.Y.Z-rc.N`으로 올리고, 사용자가 그 파일로 검증한다. 검증하는 동안 `staging`은 움직이지 않고, 개발은 `dev`에서 계속한다.
- `main`: 검증을 마친 `staging` 커밋으로 fast-forward한다. 그다음 Release 워크플로가 그 시험판의 **같은 ZIP과 SHA256**을
  정식 릴리스 `vX.Y.Z`로 올린다. 정식 릴리스 단계에서 다시 빌드하지 않는다.
- `staging`·`main`에는 작업 커밋을 직접 push하지 않는다. 이미 CI를 통과한 커밋으로 fast-forward하는 승격 push만 하고,
  승격은 사용자가 정한 때에만 한다.
- 급한 수정: `main`에서 `fix/*` 브랜치를 만들어 고치고, `main`·`dev`·진행 중인 `staging` 후보에 모두 반영한다. 후보가 바뀌면
  다시 검증한다.
- 저장소 규칙으로 막는다: `staging`·`main`은 삭제·강제 push 금지, 기록 한 줄 유지, `test`를 통과한 커밋만 받는다.
  `dev`는 여기에 PR 필수를 더한다.

## 이유

- 여러 작업을 한 작업 폴더에서 동시에 하면 커밋에 서로의 변경이 섞인다. 브랜치를 나누는 것만으로는 막히지 않고 작업 폴더를
  나눠야 한다.
- PR로 합치면(merge·squash·rebase 모두) 새 커밋이 생겨서, 검증한 커밋과 공개한 커밋이 달라진다. fast-forward로 올리면
  검증한 커밋이 그대로 공개된다.
- 같은 커밋이라도 다시 빌드하면 받는 의존성이 달라질 수 있다. 사용자가 실제로 확인한 파일을 그대로 공개해야 검증이 의미가 있다.
- GitHub에서는 시험판을 "최신 릴리스"로 지정할 수 없다. 그래서 다운로드 링크는 최신 정식 릴리스(`/releases/latest`)로 걸고, 시험판은 릴리스 목록에서 받는다.

## 결과

- CI(`ci.yml`)는 모든 PR과 `dev`·`staging`·`main` push에서 `test`를 돌린다. `staging` push에서만 패키지를 만들고 시험판을 올린다.
- 정식 릴리스는 `release.yml`을 후보 태그로 직접 실행해 만든다. `main`이 그 후보 커밋에 있어야만 실행된다.
- 사용 설명서 사이트는 `main` push에서만 배포된다. `dev`에 합친 설명서 변경은 정식 릴리스와 함께 공개된다.
- 저장소 규칙은 실수를 막는 장치다. 같은 계정 권한으로 일하는 도구도 위 규칙을 지키도록 [기여 안내](../../CONTRIBUTING.ko.md)에 적는다.
