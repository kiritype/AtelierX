# 이미지 완료 이력과 대량 접수 저장 측정 (#229)

2026-10-13, Windows/Python 3.12, `ff18262` 기준. 실제 작품·이미지·외부 서비스는 사용하지 않았다.
`tools/measure_queue_history.py --output notes/queue-history.json`으로 재현한다. 출력 부모 아래 임시 디렉터리에
합성 작업만 만들고 제거한다. 기존 앱 데이터 경로를 입력받지 않는다.

## 결과

완료 작업은 프롬프트·negative·workflow를 포함한 작업당 약 5.85KB JSON이다. 실제 `JobQueue.persist/load`를
각각 세 번 호출한 중앙값이며, 메모리는 별도 `tracemalloc` 복원 측정의 최고 Python 할당량이다(RSS/GPU 메모리 아님).
로컬 디스크·캐시·보안 프로그램에 따라 시간은 달라진다. 이전 #209 측정과 하드웨어/내용이 같다고 가정하지 않는다.

| 완료 항목 | JSON MB (10⁶ bytes) | 저장 초 | 복원 초 | 복원 최고 메모리 MB |
|---:|---:|---:|---:|---:|
| 1,000 | 5.85 | 0.036 | 0.012 | 17.6 |
| 5,000 | 29.26 | 0.189 | 0.065 | 87.8 |
| 20,000 | 117.07 | 0.847 | 0.338 | 351.2 |

기존 실행 경로는 접수 `add`, 실행 `update(running)`, 서비스 접수 `update(prompt_id)`, 완료 `update(done)`에서
최소 네 번 저장한다. 여러 항목 동시 접수의 첫 쓰기는 공유되지만 항목 실행마다 나머지 세 번은 전체 이력을 다시 쓴다.
취소·실패·재시도·추가 상태 변경은 더 쓰므로 네 번은 상한이 아니다. 20,000건 이력을 남겨 두면 위 조건에서 새 작업 하나가
세 번 쓰는 것만 약 2.54초/351MB의 직렬화 대상이 된다. 화면의 완료 표시 1,000건 제한은 디스크 보존량 제한이 아니다.

별도 접수 저장 실험은 SQLite WAL + synchronous=FULL, 대상 ID/원본 mtime/크기를 행으로 저장했다.
실행 설정은 실제 후속 구현에서 배치당 한 번 보관한다. 아래 크기는 **대기 접수 + 완료 결과 하나**이므로 전체 완료 JSON과
동일 정보량을 압축한 결과가 아니다. 개별 완료 결과는 같은 합성 작업 JSON을 행에 저장한다. 갱신마다 다른 값을 써서
SQLite의 동일 값 갱신 최적화와 구분했다.

| 접수 항목 | DB MB | 전체 최초 접수 초 | 완료 한 항목 갱신 초 | 다음 32건 조회 초 |
|---:|---:|---:|---:|---:|
| 1,000 | 0.086 | 0.004 | 0.00185 | 0.000010 |
| 5,000 | 0.365 | 0.018 | 0.00215 | 0.000010 |
| 20,000 | 1.421 | 0.076 | 0.00185 | 0.000016 |

전체 접수 저장은 선형 증가하지만 완료 한 건의 갱신은 전체 목록 크기와 분리된다. 이 실험은 파일 stat·마스크 복사·이미지
분석·ComfyUI 실행을 측정하지 않는다. #222에서 실제 접수 경로의 지연·복구·상태 변경 비용을 별도로 검증해야 한다.

## 보존 정책 비교와 #222 제안

| 방식 | 장점 | 재시도·진단 및 위험 |
|---|---|---|
| 오래된 완료 기록 자동 삭제 | 가장 작은 상태 파일 | 사용자 이력·재시도 근거 유실. 채택하지 않음 |
| 전체 JSON 압축 | 디스크 절약 | 매 상태 변경의 전체 직렬화·메모리·CPU 비용은 남음 |
| 실행 큐와 접수/완료 기록 분리 | 작은 실행 큐, 행 단위 갱신·조회 | 양쪽 저장 간 중복 방지와 재시작 복구 필요 |

- 공용 실행 큐의 **대기 5,000개**는 유지한다. 이것은 전체 접수량/완료 보존량과 다른 제한이다.
- 신규 대량 접수는 별도 SQLite에 대상·설정·원본 버전·마스크 스냅샷·작업 ID를 먼저 저장한다. 기존 queue.json과 일반 이력은
  그대로 읽는다. 신규 일괄 작업의 완료 결과/오류/실행 요청은 별도 저장 후 실행 큐에서 분리하되 사용자가 조회·재시도할 수 있게 한다.
- 처음에는 **한 접수 최대 20,000개, 미완료 접수 합계 최대 20,000개**, 실행 큐에 등록한 일괄 작업은 **합계 최대 32개**를 제안한다.
  32는 GPU 처리량 벤치 결과가 아니라 FIFO 대기 독점과 전체 스냅샷 비용을 제한하기 위한 보수적 출발점이다. 실행 슬롯은 추가하지 않는다.
- 접수 DB·마스크에는 **1GiB의 접수 전 한도와 최소 256MiB 여유 공간**을 적용한다. 이미지 결과 파일은 기존 출력 저장소를 사용하며
  완료 이력은 자동 삭제하지 않는다. 한도 초과는 접수 전에 명시적으로 거절한다. 마스크·메타데이터 길이도 제한해야 한다.
- 다음 묶음은 큐 끝에 넣어 이미 기다리는 일반 작업을 앞지르지 않는다. 여러 일괄 접수에는 돌아가며 항목을 공급한다.
- 완료분은 재실행하지 않는다. 큐 등록 전후의 장애는 안정된 항목별 작업 ID로 중복을 막는다. 실행 중 잘린 작업은 interrupted로
  보존하고 명시적 재시도만 허용한다. 접수 후 대기 중인 항목은 재개한다. 취소와 개별 파일 실패는 전체 원본/결과를 삭제하지 않는다.
- 도구 목록은 항목 2,000개 제한을 단순히 올리는 대신 행 단위 영속화 및 페이지 조회를 함께 도입한다. 원본 20,000장과 후처리 결과가
  함께 남을 수 있게 공간을 산정한다. 완료 결과를 임의 삭제해 한도를 맞추지 않는다.

이 문서는 측정과 구현 제안이다. 영구 형식 변경과 마이그레이션은 #222/0.4.0 범위에서 데이터 모델·회귀 테스트와 함께 구현한다.
